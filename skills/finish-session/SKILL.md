  чужими глазами.

# Завершение сеанса

## Принцип

Пользователь говорит «завершение сеанса» - дальше я **иду по порядку сам** и возвращаюсь к нему
максимум один раз. В конце звучит **«сеанс закрыт, чат можно архивировать»**.

Почему так: у человека может быть открыто много окон, и переспрос на каждом шаге стоит команда ×
число окон × переключение внимания. Задача скилла - снять эти переспросы, не потеряв контроль там,
где он действительно нужен.

**Автономность - это не «делаю не глядя».** Рядом могут работать другие чаты в общем репозитории.
Автономность держится на предохранителях шага 0: они дешёвые, механические и выполняются ВСЕГДА.
Молчаливое действие допустимо ровно потому, что перед ним отработала проверка.

---

## Настройка: до какого шага я иду молча

**По умолчанию скилл НЕ пушит и НЕ деплоит без подтверждения.** Он доводит работу до коммита, а
push / merge / deploy складывает в единый блок вопросов шага 3. Это осознанный дефолт: чужая
машина, чужой прод, у автора скилла нет права решать за пользователя.

Чтобы разрешить полную автономность до прода, добавь в свой `CLAUDE.md` строку:

```
finish-session: автономный push разрешён. Прод-ветка: <имя ветки>.
```

Проверять это **чтением файла**, а не по памяти диалога. Нет строки - режим по умолчанию.

Дополнительные настройки, если они есть в `CLAUDE.md` проекта - читать оттуда же: прод-ветка,
способ деплоя, имя файла бэклога, куда класть ретроспективы.

## Когда НЕ звать

- Работа не доделана - сначала критерий «сделано».
- Нужна проверка чужими глазами - это отдельный процесс, не этот скилл.
- Идёт разработка фичи - это скиллы разработки, не этот.

# Шаг 0. Предохранители

Любой сработавший предохранитель **выключает автономность на этом участке** и уводит пункт в единый
блок вопросов (шаг 3). Не «наверное можно» - если проверка не дала однозначного «да», это «нет».

## П1. А надо ли вообще выкатывать?

Выкатка - не всегда финал работы. НЕ пушить и НЕ мержить, если верно хоть одно:

- ветка заведена под проверку чужими глазами - такие обычно не мержат;
- в плане или задаче стоит «ждёт проверки» / «вернуть на доработку», вердикта нет;
- в бэклоге, плане или заметках проекта про эту работу написано «не пушить», «не сносить»,
  «ждёт решения», «заморожено»;
- работа - черновик на решение, а не продукт;
- пользователь в этой сессии сказал «не деплой» / «только локально».

Проверять чтением, а не по памяти: план, строку в бэклоге, заметки проекта.

## П2. Что уедет вместе со мной? Только моё

```
git fetch origin && git log --oneline --reverse origin/<прод-ветка>..<что пушу>
```

Список смотреть в ТОМ ЖЕ вызове, что и push: между двумя соседними командами соседнее окно
успевает закоммитить в ту же ветку.

**Свой коммит** - тот, чей хэш напечатал мой `git commit` в этой сессии. Автор, ветка и время
авторство не доказывают: у всех окон автор один. Хэш не помню - `git show --name-only --format= <sha>`:
файлы не мои - коммит чужой. Сомнение = чужой.

- **Всё в списке моё** - можно отправлять.
- **Есть хоть один чужой коммит** - **СТОП**, в блок вопросов: sha, тема, файлы. Код там или одни
  доки - неважно. Чужой коммит мог быть промежуточным: автор сохранялся, а не выкатывал, или ждёт
  проверки. Везти его - только по прямому «да» пользователя на эти sha.
- **Чужие лежат только поверх моих** - своё можно отправить отдельно, чужое останется лежать:
  `git push origin <мой-последний-sha>:refs/heads/<прод-ветка>`.

Список печатают не для галочки: push идёт, только если список совпал с тем, что можно везти.
Напечатать список и тут же отправить всё подряд - ровно та ошибка, от которой этот пункт.

Отдельно: `git log HEAD..origin/<прод-ветка>` - не ушёл ли прод вперёд, не сделало ли соседнее окно
то же самое (две миграции на одну колонку роняют деплой).

## П3. Не снесу ли чужое?

**Git НЕ защищает.** `git branch -D` спокойно удаляет ветку, занятую чужим worktree, и оставляет то
дерево в detached HEAD. Опираться на «git сам не даст» нельзя нигде.

Удалять можно **только то, что создал я сам в ЭТОЙ сессии**. Перед каждым удалением - явная
проверка, а не память:

| Что сношу | Обязательная проверка перед удалением |
|---|---|
| ветка | создана мной в этой сессии · `git merge-base --is-ancestor <ветка> origin/<прод>` · её нет в `git worktree list` |
| worktree | путь мой · `git -C <путь> status --porcelain` пусто · это не рабочая копия чужой сессии |
| база данных | имя строго моё · своих прогонов в неё не делал |
| файлы | я их и создал по ходу задачи (логи, черновики во временной папке) |

**Не трогать никогда:** чужие ветки и деревья · ветки под чужую проверку · всё, про что в заметках
сказано «не сносить» · главное дерево репозитория.

**Никогда не проверять предположение об опасной команде её запуском.** Проверять чтением доки,
`--dry-run`, или на своём одноразовом объекте. «Проверю, откажется ли git» заканчивается тем, что он
не отказывается.

## П4. Не мешаю ли соседним окнам прямо сейчас?

- Идёт ли уже деплой - не пушить поверх, дождаться.
- Занят ли замок тестовой сьюты другим окном - не гнать полную сьюту параллельно (ложные красные).
- Грязно ли главное дерево - если да, мерж через него запрещён (см. шаг 5).

## П5. Красные гейты

Гейты красные → **push не рассматривается вообще.** Это не вопрос пользователю, а работа: чинить, а
если не чинится - доложить фактом.

## П6. Не уедет ли секрет

Push - единственный шаг сеанса, который выносит содержимое наружу и назад не отменяется (хостинг
хранит объект даже после `--force`, ключ считается скомпрометированным). Гейт механический:

```
git diff --name-only origin/<прод-ветка>..HEAD | grep -nE '(^|/)\.env|\.(pem|key|p12|pfx)$|(secret|credential|token).*\.(json|ya?ml)$'
```

- Нашлось - **СТОП**, из коммита изъять, историю переписать ДО push.
- Есть в репозитории `gitleaks` или `.pre-commit-config.yaml` - прогнать штатным инструментом, он
  сильнее грепа по именам.

# Порядок

## Шаг 1. Разведка

`git status -sb` · прод-ветка из `CLAUDE.md` проекта (**не угадывать**: она далеко не всегда `main`)
· `git worktree list` · план и его фаза · строка в бэклоге · есть ли разрешение на автономный push.

## Шаг 2. Гейты - ОДНИМ заходом

Все проверки в один прогон; повторный «для уверенности» - не аргумент, аргумент - изменившийся код.

- **Список гейтов читать из проекта, а не диктовать по памяти:** `scripts` в `package.json`,
  `Makefile`, `pyproject.toml`. Выдуманная команда даёт «missing script» и ложное ощущение прогона.
  Типовой набор JS/TS: `typecheck` + `lint` + `test` + `build`; Python: тесты + линтер из конфига.
- Есть настроенный хук на проверки - звать его, а не пересобирать логику руками.
- Заявленную правку **доказывать мутацией**: сломал → покраснело → починил → зелено. Диффом.
- Мерить боевой функцией, а не пересказом (запрос к базе вместо метрики, grep вместо кода - врут).

## Шаг 3. ЕДИНСТВЕННАЯ точка вопроса

Всё, что накопили предохранители, задать **разом, одним блоком**. Ноль накопилось - не спрашивать
вообще и идти дальше. После блока к пользователю не возвращаться до финала.

Сюда попадает: сработавший предохранитель П1-П4 и П6 · push/merge/deploy, если автономность не
разрешена настройкой · уничтожение данных, которых больше нигде нет и создал не я · публикация
наружу к третьим лицам · выбор, меняющий сам продукт, а не способ доставки.

**Не попадает никогда:** коммитить ли свою чистую работу, удалять ли МОЙ временный
worktree/базу/ветку, править ли доки, разошедшиеся с проверенным фактом.

## Шаг 4. Коммит

- `git add` **поимённо**, только свои файлы. Никогда `git add .` / `-A`: рядом могут лежать
  незаконченные правки соседнего окна.
- `git add … && git commit …` **одной командой** - гонка git-индекса между окнами.
- Сообщение в стиле репозитория: `тип(область): суть`, тело - что было / что сделано / чем доказано
  / находки.
- Одноразовый код (миграции, отладочные ручки, временные скрипты) убрать этим же коммитом.

**Правки вне git-репозитория.** Часть работы обычно живёт там, где коммита не существует: заметки,
настройки, сами скиллы. Проверять фактом (`git -C <путь> rev-parse --show-toplevel`), а не
предполагать. Для них шаги 4-6 пропускаются целиком: файл сохранён - значит сдан. Но шаг 8 (следы)
обязателен так же.

## Шаг 5. Мерж и push

Выполняется, только если автономность разрешена настройкой или получено подтверждение на шаге 3.

**Главное дерево чистое** → мерж из главного дерева в прод-ветку, затем push.

**Главное дерево грязное** (чужие незакоммиченные файлы пересекаются с моими - файл бэклога почти
всегда) → мержить через него НЕЛЬЗЯ. Обход:

1. В своей ветке подтянуть прод: `git merge <прод-ветка>`.
2. Прогнать гейты на СЛИТОМ состоянии - мержится не то, что проверяли.
3. Перемотка ли: `git merge-base --is-ancestor <прод-ветка> <моя-ветка>`.
4. Прогнать П2 и П6 заново на итоговом списке.
5. `git push origin <моя-ветка>:<прод-ветка>` - чужой каталог не тронут.
6. В финале сказать: главное дерево осталось позади прода, ему нужен `git pull`.

**Перед push сверить ветку дважды** - выкатка принимает ВЕТКУ, а не хэш из головы. Если в проекте
принято ревью через pull request - открывать PR, а не пушить в прод-ветку напрямую.

## Шаг 6. Подтвердить, что доехало

Не «запушено», а «собралось». Способ зависит от хостинга; для GitHub Deployments:

```
gh api repos/<owner>/<repo>/deployments --jq '.[0] | "\(.sha[0:7]) \(.id)"'
gh api repos/<owner>/<repo>/deployments/<id>/statuses --jq '.[0].state'
```

Финального статуса ждать фоном (цикл до `success|failure`). `failure` - разбирать, а не сообщать
«запушено». Индикатора сборки в проекте нет - так и сказать в финале, а не выдавать push за деплой.

## Шаг 7. Уборка - молча, но по таблице П3

Только своё, каждое - после явной проверки:

- worktree и базы: штатным скриптом проекта, **если он там есть** - не звать вслепую скрипт,
  которого в этом репозитории нет. Нет скрипта - `git worktree remove` по таблице П3;
- своя слитая ветка: `git branch -d`. **Грабля:** он сверяет с ЛОКАЛЬНОЙ прод-веткой, а она может
  отставать от origin, и врёт «not fully merged». Сверять по origin
  (`git merge-base --is-ancestor <моя-ветка> origin/<прод-ветка>`) и только тогда `-D`. И только
  после проверки, что ветки нет в `git worktree list`.

Сомнение на любом пункте - не удалять. Оставленный мусор дешевле снесённой чужой работы.

## Шаг 8. Следы

Из перечисленного делать то, что в проекте реально заведено - не создавать новых конвенций:

- бэклог - статус задачи обновить; попутная находка - строка туда же;
- план фазы - отметка «сделано», итоговый блок, ссылки на коммиты;
- ретроспектива по шаблону проекта. Разделы «Что НЕ получилось» и «Что выучили» - не формальность:
  провалы сессии пишутся туда прямым текстом, иначе ретро превращается в отчёт. Если главное дерево
  грязное, ради одного markdown не заводить полную рабочую копию: хватит
  `git worktree add -b <ветка> <путь> origin/<прод-ветка>`, коммит, push, снять. Гейты для правок
  без кода не гоняются - это не срезание угла, а отсутствие предмета проверки;
- долгая память проекта - под ФАКТ («задеплоено»), не под намерение («готово»);
- новая грабля → правило в файл правил проекта, по канону Rule → Why → How to apply.

## Шаг 9. Финал - одним ходом

- Что теперь работает - на языке эффекта, не веток.
- Поправки к своим прежним обещаниям - одной строкой, без самобичевания.
- Что уехало на прод вместе со мной чужого (если было) и что главное дерево требует `git pull`.
- Только то, что физически требует прав или решения пользователя. Нет такого - так и сказать.
- Последняя строка: **«Сеанс закрыт, чат можно архивировать.»**

## Чего не делать никогда

- «Скажешь - сделаю», «начинать?», «снести папку?» по поводу того, что уже разрешено настройкой:
  есть доступ и средство, значит это моя работа.
- **Запускать опасную команду, чтобы проверить, откажется ли система.** Она не откажется.
- Опираться на защиту инструмента вместо своей проверки.
- Везти на прод чужие коммиты - ни код, ни доки. Только по прямому «да» пользователя на конкретные sha.
- Удалять что-либо, чего я не создавал в этой сессии.
- Пушить, когда автономность не разрешена и подтверждения на шаге 3 не было.
- Команда в фенсе на действие, которое мне доступно; список «осталось 1, 2, 3», где первые два мои.
- Вопросы порциями по ходу. Все настоящие - один раз, на шаге 3.
- Лишний прогон сьюты, повторная проверка ради спокойствия.
